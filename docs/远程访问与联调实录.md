# 远程访问与联调实录

这份文档记录 Monet Chat 1.1.0 打通「手机在外网、电脑在家里」的完整过程，包括成功路径、失败路径和最后为什么改成 WebSocket。以后换网络、换机器，按这份记录复现即可。

> 文中 `<...>` 是占位符，不要直接照抄成真实地址。Quick Tunnel 的域名每次重启都会变。

## 1. 目标与最终结构

目标：

- 手机用浏览器或 APK，在外网打开；
- 电脑端保持在线；
- 双方进入同一个房间，消息端到端加密；
- 不把聊天内容交给中转服务器。

最终链路：

```text
手机浏览器 / APK
      │  HTTPS + WSS
      ▼
Cloudflare 边缘（Quick Tunnel）
      │  已注册的 cloudflared 连接
      ▼
Windows PC: cloudflared.exe
      │  127.0.0.1:4175
      ▼
Monet Chat server.mjs  ── 只转发房间、SDP/ICE、在线状态
      │
      ▼
PC 浏览器（另一个 P2P 节点）
      │  WebRTC DataChannel（加密后直连）
      ▼
手机 WebRTC
```

要点：

- 服务器只做**信令**和静态页面，不接触消息明文。
- 真正的聊天走 WebRTC DataChannel；远端能否直连取决于 NAT，失败时仍需要 TURN。
- Cloudflare Tunnel 解决的是「手机怎么找到这台电脑的 4175 端口」，不是消息中继。

## 2. 本机启动

在 `monet-chat` 目录：

```powershell
npm install
npm start
```

默认监听 `0.0.0.0:4173`。如果要和本记录一致，用 4175：

```powershell
$env:PORT='4175'
node server.mjs
```

检查：

```powershell
curl.exe http://127.0.0.1:4175/api/health
# {"ok":true,"clients":0,"rooms":0,...,"version":"1.1.0"}
```

局域网内手机可以先试：

```text
http://<PC-LAN-IP>:4175
```

Windows 防火墙如果弹出提示，要允许**专用网络**。如果之前点过“取消”，需要管理员权限重新放行：

```powershell
New-NetFirewallRule -DisplayName "Monet Chat 4175" -Direction Inbound -Protocol TCP -LocalPort 4175 -Action Allow
```

这条命令需要“以管理员身份运行”的 PowerShell；普通权限会报 `requires elevation`。

## 3. 为什么不用公网 IP + 端口映射

一开始试的是最直接的方式：

1. 查公网 IP；
2. 在路由器上把 `4175` 映射到 PC 的局域网 IP；
3. 手机访问 `http://<公网IP>:4175`。

实际环境里：

- 路由器 UPnP 没有可用的 `StaticPortMappingCollection`；
- 用 `nat-upnp` 能创建映射，但 `GetExternalIPAddress` 返回的是 `192.168.1.5`，说明**路由器本身还在上一层 NAT 后面**（双层 NAT）；
- 从本机访问公网 IP 的 `4175` 会超时（没有 hairpin NAT）；
- 防火墙规则又需要管理员权限。

所以公网 IP 方案在这个网络下不可行。除非能登录**上一层路由器**再做一次端口映射，或者让运营商给公网可达地址。

> 如果换到单层 NAT 的网络，这一步仍然是最省事的方案：路由器端口映射 + 防火墙放行即可。

## 4. Cloudflare Quick Tunnel

### 4.1 准备 cloudflared

仓库不提交 `cloudflared.exe`，需要单独下载到 `toolchain/`：

```powershell
curl.exe -L --fail -o toolchain\cloudflared.exe `
  https://github.com/cloudflare/cloudflared/releases/latest/download/cloudflared-windows-amd64.exe
```

### 4.2 直接启动（不指定 edge）

```powershell
toolchain\cloudflared.exe tunnel --url http://127.0.0.1:4175 --no-autoupdate
```

这台机器上会失败：

```text
lookup argotunnel.com: no such host
ensure that argotunnel.com is returning "origintunneld" service records
```

系统 DNS 对 Cloudflare 的 SRV 记录不完整。**不要在这里反复重试**，直接指定 edge IP。

### 4.3 解析真实 edge IP

```powershell
Resolve-DnsName region1.v2.argotunnel.com -Server 1.1.1.1 -Type A
```

会得到一组 `198.41.192.x`。取一个：

```text
198.41.192.77
```

### 4.4 指定 edge 启动

```powershell
$log = "$PWD\cloudflared-ws.log"
toolchain\cloudflared.exe tunnel `
  --url http://127.0.0.1:4175 `
  --no-autoupdate `
  --protocol http2 `
  --edge 198.41.192.77:7844 *> $log
```

日志里要看到：

```text
Registered tunnel connection connIndex=0 ... ip=198.41.192.77 location=lax05 protocol=http2
```

以及分配到的地址：

```text
https://<random-words>.trycloudflare.com
```

这个地址就是手机要访问的公网入口。

### 4.5 验证隧道是否真的通

先解析这个随机域名在 Cloudflare 的真实 IP：

```powershell
Resolve-DnsName <random-words>.trycloudflare.com -Server 1.1.1.1 -Type A
```

会得到 `104.16.230.132` / `104.16.231.132` 一类的地址。然后用 `--resolve` 绕过本机被污染的 DNS：

```powershell
$h = "<random-words>.trycloudflare.com"
curl.exe --resolve "${h}:443:104.16.230.132" "https://$h/api/health"
```

返回：

```json
{"ok":true,"clients":0,"rooms":1,"uptime":8180,"version":"1.1.0"}
```

才说明隧道真的到了本机，而不是 Cloudflare 的错误页。

### 4.6 一个非常关键的坑：用错边缘 IP 会返回 403

如果拿 `trycloudflare.com` 域名的 IP 去套任意一个 Cloudflare 地址，可能返回：

```text
HTTP/1.1 403 Forbidden
error code: 1034
```

`1034` 不是“隧道没连上”，而是**你请求的 Cloudflare 边缘不知道这个主机名对应的隧道**。正确做法是：

1. 用 `1.1.1.1` 解析**当前这个随机域名**；
2. 用解析出来的 IP 做 `--resolve`；
3. 不要复用上一个隧道的 IP。

我们第一次用 `104.16.132.229` 一直 403，换成 `104.16.230.132` 立刻 200。

### 4.7 手机 DNS 被污染时

如果手机打开公网域名失败，但电脑用 `--resolve` 能通，通常是手机 DNS 返回了 ISP 的拦页面。

处理：

- Android：设置 → 网络 → 私人 DNS → `1.1.1.1`；
- 或先开 VPN/代理再打开；
- 不要用 `http://`，Quick Tunnel 只提供 HTTPS。

## 5. 房间码

服务器启动后，创建 DM 房间：

```powershell
curl.exe -X POST http://127.0.0.1:4175/api/rooms `
  -H "Content-Type: application/json" `
  -d '{"kind":"dm","name":"远程测试"}'
```

返回：

```json
{"room":{"code":"D-XXXX-XXXX","kind":"dm","name":"远程测试","online":0}}
```

两个端都用同一个 code：

- PC：`http://127.0.0.1:4175/?join=D-XXXX-XXXX`
- 手机：`https://<random-words>.trycloudflare.com/?join=D-XXXX-XXXX`

第一次打开会要求创建身份，填名字后会自动加入。

> 房间只存在内存里，服务器重启就没了；TTL 24 小时。手机和电脑必须同时在线，房间才有两个成员。

## 6. 为什么最后改成 WebSocket

这是整个联调里最隐蔽的问题。

最初信令用的是 SSE（`GET /api/events`，`text/event-stream`）。局域网完全正常，但走 Cloudflare Tunnel 时：

- `/api/health` 正常 200；
- `/api/events` 用 `curl -N` 等 6 秒、25 秒都是 **0 字节**；
- 手机页面一直显示“信令服务器无法连接”。

原因：Cloudflare 边缘会缓冲 SSE 的小响应，`res.write()` 的 `retry:`、`welcome` 都到不了浏览器。SSE 注释填充 8KB 也没有解决。

解决：**信令改走 WebSocket**。

服务端：

- `server.mjs` 使用 `ws` 的 `WebSocketServer({ noServer: true })`；
- `server.on('upgrade')` 只接受 `/ws`；
- 为了复用原来的房间/信号逻辑，给 WebSocket 包了一个“假 res”：
  - `write(chunk)` 把 SSE 文本拆成 `event:` / `data:`；
  - 转成 `{"event":"...","data":...}` 发给 WebSocket；
- 原来的 `handleEvents()`、房间广播、心跳、掉线宽限全部继续复用。

客户端：

- `src/signaling.js` 新增 `connectWS()`；
- 优先用 `WebSocket`，`file://` 场景才回退 SSE；
- 断线后 1.8 秒自动重连；
- `welcome` 到达才算 `online`。

验证：

```text
A: 电脑本地 http://127.0.0.1:4175
B: 模拟手机，走公网 https://<random-words>.trycloudflare.com
结果：双方 subtitle 都是“在线”，A 发的消息 B 能收到。
```

## 7. 常见现象对照表

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 隧道命令报 `lookup argotunnel.com: no such host` | 系统 DNS 没有 Cloudflare SRV | 用 `--edge 198.41.192.77:7844` |
| 公网域名 403 / `error code: 1034` | 用错边缘 IP，或域名不是当前隧道 | 用 `1.1.1.1` 解析当前域名 |
| 公网域名打开是 ISP 广告/空页 | 本地 DNS 污染 | 手机私人 DNS `1.1.1.1` 或开 VPN |
| `/api/health` 200，但页面“信令服务器无法连接” | Cloudflare 缓冲 SSE | 改用 WebSocket（当前代码已改） |
| 本机访问公网 IP:4175 超时 | 双层 NAT / 没有 hairpin | 不要用公网 IP，走隧道 |
| UPnP 外部 IP 是 `192.168.x.x` | 路由器还在上一层 NAT 后面 | 需要上一层路由器映射 |
| 防火墙加规则报 `requires elevation` | 普通权限 | 管理员 PowerShell 执行 |
| 手机能进页面但一直“离线” | 信令未连上 / 房间码不对 | 看 `#net-chip`，确认 `/ws` 可访问 |
| 两端都在线但消息不通 | WebRTC NAT 失败 | 配置 TURN；或先在同一 Wi-Fi 验证 |

## 8. 安全提醒

- Quick Tunnel 的域名是**公开可访问**的，任何人拿到 `?join=` 链接都能进入同一个房间；房间码就是门票，不要公开发到群里。
- 信令服务器只看到房间成员、SDP/ICE、在线状态；消息内容仍然是 E2E 加密的。
- 但 Quick Tunnel 本身不提供访问控制，正式使用建议：
  - 用 Cloudflare Named Tunnel + Access；
  - 或自建带鉴权的信令服务器；
  - 或只在内网/Tailscale 中使用。
- 当前身份私钥保存在本机 IndexedDB，换浏览器/清数据会丢失；重要身份请用设置里的导出功能备份。

## 9. 最短复现命令

```powershell
# 1. 启动服务
$env:PORT='4175'
node server.mjs

# 2. 另一个窗口起隧道
toolchain\cloudflared.exe tunnel --url http://127.0.0.1:4175 `
  --no-autoupdate --protocol http2 --edge 198.41.192.77:7844

# 3. 从日志取 URL，手机打开
# https://<random-words>.trycloudflare.com/?join=<ROOM-CODE>
```

电脑端保持 `http://127.0.0.1:4175/?join=<ROOM-CODE>` 打开，两端都显示“在线”即可。

## 10. 发布到 GitHub 的补充记录

本次发布也踩了几个坑，留作参考：

- 本机 `node` 可能被 Electron/桌面壳包装，`process.execPath` 不是真正的 Node；构建 EXE 时要用独立的 `toolchain\node\node-v24.21.0-win-x64\node.exe`。
- `electron-builder` 下载 Electron 运行时可能超时；可在 `package.json` 的 `build` 里指定 `"electronDist": "node_modules/electron/dist"`。
- GitHub 的 OAuth/设备授权在这台机器上多次被代理重置；设备码流程（`https://github.com/login/device`）比 localhost 回调更稳。
- 源码用 `git push`，大文件（APK/EXE/Linux tar）用 GitHub Release API 上传，避免把二进制塞进 Git 历史。
- Release 资源上传接口：

```text
POST https://uploads.github.com/repos/<owner>/<repo>/releases/<id>/assets?name=<file>
Authorization: Bearer <token>
Content-Type: application/octet-stream
```

> 不要把 token、`keystore.properties`、`*.jks` 提交进仓库；这些已在 `.gitignore` 中排除。

## 11. 当前限制

- Quick Tunnel 地址每次重启都变，需要重新发给手机。
- APK 内置的默认服务器地址是开发机 LAN 地址；外网使用时要在首次启动页填公网隧道地址。
- 群聊最多 12 人；超过后服务器拒绝加入。
- 没有 TURN 时，部分运营商/对称 NAT 下 WebRTC 可能连不上；需要自建 TURN 并在设置里填写。
- 静态 ECDH 没有前向保密；后续可以升级为双棘轮。
